<Lead>A development container gives your editor consistent tools. An execution environment gives a playbook consistent runtime dependencies. Learn to identify both.</Lead>

## Prepare a project

**Goal:** run the Git lesson's `hello.yml` with tools supplied by a container, then run it through a separately selected execution image. The playbook only prints a message, so you can learn the workflow without changing a remote host.

Use a **desktop machine** for the editor portion. The terminal-only workstation VM can run the later navigator exercise. A container needs a working engine on the machine that starts it.

1. Install [VS Code](https://code.visualstudio.com/docs/setup/setup-overview) and a supported Docker engine. Run `docker info` in your desktop terminal: it must show server information before you proceed. If it reports a connection or permission error, fix the engine setup first.
2. In VS Code's Extensions view, install **Dev Containers** (Microsoft) and **Ansible** (Red Hat). Dev Containers starts the editor environment; the Ansible extension supplies YAML and automation editing support.
3. Open a folder containing the Git lesson's `hello.yml`. On a different machine, copy that small project or clone a remote reachable from that machine. The local bare remote exists only on the machine where you created it.
4. Inside the project, create the directory `.devcontainer` and the file below. This tells VS Code which tool image to use and which extension to install inside it.

```json title=".devcontainer/devcontainer.json"
{
  "name": "Ansible practice",
  "image": "ghcr.io/ansible/community-ansible-dev-tools:latest",
  "customizations": {
    "vscode": {
      "extensions": ["redhat.ansible"]
    }
  }
}
```

Open the Command Palette and choose **Dev Containers: Reopen in Container**. The first pull can take several minutes. Once ready, the bottom-left remote indicator should identify the container. Open a **new integrated terminal**: its commands now use container tools, while your project files remain available in the editor.

<Reveal title="Use Podman or pin a tested image">

Podman users should follow the [community development-container guide](https://docs.ansible.com/projects/dev-tools/container/) and its engine-specific sample configuration. Container-in-container workflows need additional engine integration; the simple local play below does not start another container.

The public image requires no registry account. The `latest` tag can move. On the host, inspect the image after pulling it (`docker image inspect ghcr.io/ansible/community-ansible-dev-tools:latest --format '{{json .RepoDigests}}'`, or the Podman equivalent). Record the returned image reference and replace the tag with its `@sha256:...` digest after testing.

</Reveal>

## Prove where the tools run

Run these commands in the **container's integrated terminal**:

```bash
pwd
ansible --version
ansible-navigator --version
ansible-lint --version
ansible-playbook hello.yml --syntax-check
ansible-playbook hello.yml
```

`pwd` should identify the mounted project. The version commands identify the tools from this image. The syntax check should accept the playbook; the run should print your message with `failed=0`. Record these versions alongside the workstation versions from the previous lesson. They can differ without changing this small playbook's behavior.

Remote labs need network and SSH access **from the runtime that runs the playbook**. A desktop outside the sealed lab cannot directly reach its managed hosts. Use this localhost exercise on the desktop and use workstation for remote labs.

## Configure navigator deliberately

First, make navigator use the tools already installed in the development container. In the project, save:

```yaml title="ansible-navigator.yml"
ansible-navigator:
  mode: stdout
  execution-environment:
    enabled: false
  playbook-artifact:
    enable: false
```

These settings produce terminal output, avoid starting a second container, and avoid saving run artifacts. Check the effective settings, run the playbook, and read a module's documentation:

```bash
ansible-navigator settings --mode stdout
ansible-navigator run hello.yml
ansible-navigator doc ansible.builtin.copy --mode stdout
```

The run should print the same message. Documentation should describe the copy module rather than execute a task. A project settings file takes precedence over the home settings file; inspect the effective settings if the observed behavior differs.

## Try a separate execution environment

On **workstation**, use a folder with `hello.yml` and a working Podman engine. Check `podman info` first. Run:

```bash
ansible-navigator run hello.yml --ee true \
  --execution-environment-image ghcr.io/ansible-community/community-ee-minimal:latest \
  --mode stdout
```

Navigator now starts the chosen execution image and runs the playbook inside it. The explicit command options override the local project's disabled-EE setting. Expect a pull on the first run and the same debug message afterward. If pulling fails, check internet access and the image name before changing the playbook.

**Verify the boundary:** run `ansible-navigator exec --ee true --execution-environment-image ghcr.io/ansible-community/community-ee-minimal:latest --mode stdout -- ansible --version`. Record the engine from inside that image. A minimal image may omit collections used by later labs; workstation's installed collections are not automatically installed in it.

**Try independently:** change the debug message, predict the result, and run both ways again. Explain which files are shared and which tools belong to each runtime.

## When newer templates behave differently

Core 2.19 introduced stricter templating and conditional checks. Use actual booleans for conditions, keep `{{ }}` out of `when`, and do not assume text from a command is a trusted template. Reproduce an error with the smallest playbook before changing a whole project.

## Recap

The development container supplies your editing tools. An execution environment supplies a playbook's runtime dependencies. Identify each runtime, test a small playbook, and record the image you used before moving to remote automation.
